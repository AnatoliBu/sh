# TODO-driven AI coding pipeline — исследование и архитектура

> Статус: концепт / техническое исследование, а не готовая интеграция. Зафиксировано по обсуждению 2026-11-03.
>
> Цель — резко снизить расход токенов большой модели: она понимает архитектуру и оставляет локализованные задачи в комментариях кода, а дешёвые локальные или бесплатные модели реализуют их в автоматическом фоновом цикле.

## Основные решения

1. **Большая модель = архитектор.** Анализирует репозиторий, выбирает место изменения, учитывает архитектурные инварианты и оставляет исполняемые комментарии TODO с ограничениями и критериями приёмки. Не гоняет сборки и не исправляет мелкие ошибки по кругу.
2. **Комментарии в исходниках = источник задач.** Никаких отдельных Markdown-файлов на каждый TODO. SQLite может хранить очередь, состояние, попытки и метрики, но не дублирует постановку.
3. **Фоновый daemon** сканирует новые и изменённые специальные TODO, дедуплицирует по стабильному ID, выбирает задачу, создаёт git worktree и контролирует лимиты попыток.
4. **Panda Router** — кандидат для выбора исполнителя. Роутер возвращает модель и fallback ladder, но сам НЕ реализует код, НЕ запускает тесты и НЕ доказывает корректность патча.
5. **Исполнители:** OmniCoder 2 9B (уже используется через Ollama/OpenCode), Qwen 3.5 9B и иные реально доступные бесплатные облачные/дешёвые модели.
6. **Аппаратный baseline — 8 ГБ VRAM.** На данном окружении OmniCoder уверенно работал с контекстом до 32K, но это не доказательство стабильности более длинных окон или полного размещения на GPU. Q4_K_M ≈5.7 GB весов, плюс нужен KV-cache и память runtime.
7. **Два режима на A/B-тесте:** полноценный агент через OpenCode с tool calling и ограниченный patch-generator, которому оркестратор подаёт конкретные файлы и применяет diff сам.
8. **Результат принимают детерминированные проверки, а не обязательно новая платная LLM.** Большую модель вызывать на архитектурных конфликтах, неоднозначном требовании или после исчерпания разумных попыток.
9. **Роутинг исполнителя и решение о доппроверке — разные предсказания.** У них разные входные признаки, метки и цена ошибок.
10. **Не делать автоматический merge без политики допуска.** Зафиксировать проверенный diff/PR; high-risk изменения требуют отдельного контроля.

## Архитектура

~~~mermaid
flowchart TD
    A[Большая LLM: архитектура, инварианты, точки интеграции] --> T[TODO(agent) в исходном коде]
    T --> S[TODO scanner: ID, diff, дедупликация]
    S --> Q[(SQLite: очередь, статусы, логи)]
    Q --> R[Panda Router: выбрать исполнителя]
    R --> L[Локальные 9B: OmniCoder / Qwen]
    R --> F[Бесплатные / дешёвые API-модели]
    L --> E[OpenCode agent ИЛИ patch-worker]
    F --> E
    E --> W[Изолированный git worktree]
    W --> V[Компиляция + статика + unit + integration + contracts]
    V -->|не прошло| X{Можно исправить в рамках бюджета?}
    X -->|да| E
    X -->|нет| Z[Эскалация человеку / большой LLM]
    V -->|всё зелёное| D[Политика и оценка остаточного риска]
    D -->|низкий риск| P[Проверенный patch / PR]
    D -->|высокий / неопределённый| H[Доппроверка]
    H -->|успех| P
    H -->|блокер| Z
    Z -.->|новая постановка| A
    P --> M[(История исходов: качество, время, токены)]
    Z --> M
~~~

**Параллельность:** worktree допускает несколько изолированных задач, но для одной 8GB GPU исходно выгоднее один активный локальный исполнитель. Планирование сильной моделью — при постановке или конфликте, не повторно для каждого шага.

## Исполняемый TODO

Пример формата (синтаксис и сканер пока проектные):

~~~java
// TODO(agent:PAY-017)
// scope: PaymentMethodMapper.java#getMethod
// implement: For unknown payment method return UNKNOWN; never throw.
// constraints: Do not change public API or existing enum values.
// acceptance: Existing methods unchanged; null and unknown deterministic.
// tests: PaymentMethodMapperTest (known, unknown, null)
~~~

Парсить только явный маркер TODO(agent:...), а не все человеческие TODO/FIXME. ID + хеш текста позволяют обнаружить изменение задания. Удаление комментария **не равно** успешной реализации: закрытие — это успешная проверка патча и сохранённый исход. Не запускать произвольные команды из чужих комментариев. Маленькому агенту передавать один TODO, нужные файлы, зависимости, acceptance checks и минимальный repo context; рабочая начальная гипотеза 5–12K токенов, не подтверждённый оптимум. Задачи на несколько сервисов или новые архитектурные решения передекомпозирует сильная модель.

## Детерминированные уровни проверки

| Уровень | Автоматически проверяем | Инструменты (примеры) | Что остаётся за пределами |
|---|---|---|---|
| Компиляция и статика | Типы, стиль, известные баг-паттерны, запрещённые API | javac, Maven/Gradle, Checkstyle, PMD, SpotBugs, Error Prone, Semgrep | Соответствие бизнес-требованию |
| Структура и контракты | Scope diff, изменённые методы, публичные API, несовместимые схемы | Git, JavaParser/Spoon, OpenAPI/schema diff | Скрытая поведенческая несовместимость |
| Unit | Ветви, крайние случаи, локальные инварианты и переходы | JUnit 5, Mockito, JaCoCo | Настоящая БД, Kafka, сеть |
| Integration | Транзакции, сериализация, работа с PostgreSQL/Redis/Kafka, wiring | Spring Boot Test, Testcontainers, WireMock | Полный production-набор сбоев и нагрузку |
| Contract / E2E | Ключевые пользовательские сценарии и межсервисная совместимость | Pact, OpenAPI, существующие E2E | Нетестируемые сценарии |
| Углублённые, выборочно | Качество тестов, property-based проверки, межпоточные крайности | PIT, jqwik, JCStress, fault injection | Доказательство отсутствия всех ошибок |

**Остаточные риски при зелёных проверках:** неверно понятое требование, отсутствующий тестовый оракул, неучтённые сценарии, гонки и порядок событий, differences в production-конфигурации, безопасность и бизнес-инварианты, не представленные тестами. Покрытие строк НЕ означает корректность. Особые правила для платежей, безопасности, миграций, публичных контрактов, доставки событий и идемпотентности.

## Решение о дополнительной проверке: признаки без LLM

Python-коллектор запускает инструменты и объединяет отчёты в структурированный JSON. Минимальные 12 признаков:

| # | Признак | Источник |
|---|---|---|
| 1 | Число изменённых файлов | Git |
| 2 | Добавленные / удалённые строки | Git |
| 3 | Изменённые методы | JavaParser/Spoon + diff |
| 4 | Изменение публичного API/контракта | AST/OpenAPI diff |
| 5 | Затронуты транзакции/конкурентность (эвристика) | AST + правила |
| 6 | Новые предупреждения статики | SpotBugs/PMD/Semgrep |
| 7 | Покрытие изменённых строк | JaCoCo + diff |
| 8 | Покрытие изменённых ветвей | JaCoCo + AST |
| 9 | Результаты unit | JUnit XML |
| 10 | Результаты integration | JUnit XML / CI |
| 11 | Число попыток/исправлений | SQLite / daemon |
| 12 | Модель и режим исполнителя | Runner / router |

Отсутствие данных = unknown/null, а не 0. Критичность бизнес-области задаётся правилами/метаданными, не угадывается по файлу. Сначала работают hard gates: если компиляция/обязательные тесты падают, задача идёт обратно исполнителю без Decision Model. После зелёного результата — политика и *в перспективе* модель для прогноза **P(существенный дефект остаётся | признаки, история)**.

Важно: **готовый Panda Router не является готовым классификатором остаточного риска конкретного diff**. Для второго решения нужны отдельная модель/правила, датасет независимых проверок и откалиброванные вероятности. Тестировать надо не только «сколько задач отправлено на review», но и пропуск серьёзных дефектов. Часть низкорисковых задач отправлять на независимый review случайным образом, чтобы избежать selection bias.

## 8GB-эксперимент: где реальный предел маленьких моделей

- Кандидат 1: OmniCoder 2 9B, Ollama carstenuhlig/omnicoder-2-9b, основан на Qwen3.5-9B; Q4_K_M карточка заявляет 32K контекст в настройках. Self-reported бенчмарки — только гипотеза, не подтверждение на локальной Java-разработке.
- Кандидат 2: Qwen3.5-9B с подходящей для 8GB квантизацией. Другие варианты добавлять только после проверки доступности и совместимости.
- Лесенка: один метод по контракту → крайние случаи/тест → 2–3 файла → интеграция Spring → Kafka/транзакции → задачи на пересмотр API/архитектуры. Последние могут быть вне зоны дешёвого исполнителя.
- Сравнить agent vs patch, контекст 5/8/12/16/32K, Q4/Q5 если аппаратно возможно, число файлов, число ретраев. Замерять pass@1, pass after retries, независимый review, elapsed time, токены, VRAM/RAM, категории ошибок, стоимость завершённой задачи.
- Тесты должны быть независимым oracle, иначе модель может писать «удобные» тесты себе самой и формально проходить.

## План реализации (не начат)

**A. MVP без Router.** 10–20 небольших Java-задач с критериями принятия; синтаксис TODO(agent), scanner, state machine, worktree, лимиты retries; компиляция, unit/integration и JSONL-журнал. Два режима executor для сравнения.

**B. Замеры модели.** Контекст 5–32K, разные границы scope; OmniCoder vs Qwen; валидация скорости, ошибок tool calling, сложности задач. Не полагаться на общие benchmark как замену тестам своей системы.

**C. Panda Router.** Интеграция модели маршрутизации в очередь, доступные model cards, учёт VRAM/внешних лимитов, fallback и эскалации. Сравнить с фиксированным дешёвым исполнителем по полной стоимости успешной задачи, включая неудачные прогоны.

**D. Остаточный риск.** Python-пайплайн 12 признаков, правила критичности, выборочная проверка части «зелёных» low-risk задач, метки реальных дефектов. Классификатор сначала в shadow mode. Сравнить калибровку/recall и стоимость review с жёсткими правилами.

## Референсы, первоисточники и ограничения

1. [OpenGiraffe](https://github.com/zclllyybb/OpenGiraffe) — реальный daemon: TODO/FIXME discovery, SQLite, git worktrees, OpenCode, planner→coder→reviewer, retries. Для нашей схемы встроенный постоянный planner и несколько LLM-reviewers, вероятно, избыточны.
2. [OpenGiraffe config](https://github.com/zclllyybb/OpenGiraffe/blob/master/config.yaml.template) — маршрутизация моделей по complexity, worktrees, retries и настройка авто-сканирования TODO. В шаблоне auto_scan_todos = false; всё нужно конфигурировать.
3. [OpenHands — automated TODO management](https://github.com/OpenHands/software-agent-sdk/blob/main/examples/03_github_workflows/03_todo_management/workflow.yml) — существующий пример GitHub Actions, который ищет TODO(openhands) в коде и создаёт PR с реализацией. Не то же самое, что постоянный daemon.
4. [Panda Router / PandaOrchestrator](https://github.com/AICodeKing/PandaOrchestrator) — локальная маршрутизация на базе небольшой ONNX-модели + model cards, исходно ~31 MB; выбирает модель, не выполняет код. Ограничения точности следует проверять на своих outcomes.
5. [Panda Router — outcome report](https://github.com/aicodeking/PandaOrchestrator/blob/main/data/outcomes/REPORT.md) — в отчёте для **v1** сообщается слабая корреляция оценки сложности с реальными SWE-bench outcomes (Spearman ~0.046 на 2594 задачах); это **не** измерение нынешней v4 и не оценка нашего TODO workflow.
6. [OmniCoder 2 9B — Ollama](https://ollama.com/carstenuhlig/omnicoder-2-9b) и [оригинальный model card](https://huggingface.co/Tesslate/OmniCoder-2-9B) — параметры и самоописание. Результаты benchmark у автора не заменяют независимые прогоны на своей GPU.
7. [OpenCode](https://opencode.ai/) — runner/agent harness, требует собственной интеграции очереди и хуков.
8. Проверки Java: [JaCoCo](https://www.jacoco.org/jacoco/), [PIT](https://pitest.org/), [Testcontainers](https://testcontainers.com/), [Semgrep](https://semgrep.dev/).

**Факт:** TODO-комментарии как задачи для автоматического агента уже используются, как минимум в примерах OpenGiraffe и OpenHands. **Не установлено:** опубликованный воспроизводимый результат экономии токенов именно цепочки «большая модель пишет кодовые TODO → Router → локальные 9B → тесты → selective review». Это гипотеза для измерения.

## Открытые вопросы

- Периодический polling или событийные hooks OpenCode/Git? Как не запускать обработчик на незавершённом изменении файла?
- Формальный контракт TODO (ID, scope, dependencies, acceptance checks), обработка перемещения/удаления маркеров.
- Нужно ли писать независимые тесты сильной моделью во время постановки — потенциально выше расход токенов, но ниже риск ложного pass.
- Как согласовать несколько TODO, которые затрагивают общие файлы/контракты?
- Пределы Q4/Q5 и 32K на конкретном 8GB GPU при agent tool calling и сборке Java.
- Доля ручного контроля для high-risk изменений и политика автоматического PR.
- Нужна ли отдельная Decision Model для оценки остаточного риска или достаточно жёстких правил + статистического порога.
- Фактическое снижение платных токенов, стоимость GPU-времени и доля пропущенных дефектов — всё ещё нужно измерить.
